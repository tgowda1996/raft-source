# 07 — The `raft` CLI, agent knowledge (the Manual), and raft-sdk

## 1. What it is

The `raft` CLI (`packages/cli`) is the agent's only way to act in the workspace. The daemon system prompt says: "Always communicate through `raft` CLI commands. This is your only output channel: text you produce outside a `raft` command is not delivered to anyone" (`packages/daemon/src/drivers/systemPrompt.ts:84`). An agent runtime (Claude Code, Codex, Kimi, etc.) calls `raft message send`, `raft task claim`, `raft manual get` and similar commands through its ordinary shell/Bash tool. Each command is a short-lived Node process that makes typed HTTP calls to `/internal/agent-api/*` on the Raft server. For daemon-managed agents the calls go through a localhost credential proxy in the daemon, so the agent never holds the real key. "The Manual" (`manual/agent-knowledge/*.md`, `manual/recipes/**`) is a set of markdown docs compiled into the server. Agents fetch it on demand with `raft manual get|search`, and every lookup is logged with the agent's stated intent and reason (`agent_knowledge_events`). `@botiverse/raft-sdk` is a thin, publishable TypeScript wrapper over the same shared Agent API contract, for bots and external agents that are not shell-driven.

## 3. Data model

- **`agent_knowledge_events`** (`packages/server/src/db/schema.ts:5593-5640`, migration `drizzle/0094_agent_knowledge_events.sql` + later ones). Columns: `id`, `server_id` FK, `agent_id` FK, `computer_id`, `doc_id`, `topic_or_path` (the literal query), `doc_version` (`sha256:<16 hex>` of served content), `doc_state` enum(draft/published/deprecated/retired), `source` enum(`cli` only), `status` enum(success/not_found/denied/error), `requested_at`, `latency_ms`, `response_bytes`, `turn_id`, `trace_id`, `intent`, `reason`, `context_contract_version` (`manual-context-v1` or null), `operation` enum(get/search; set by the route, not the caller), `resolution` enum(exact_id/alias/token_route/lexical/concept_expansion/typo_correction/mixed/language_gate). Indexes on (agent, requested_at), (server, requested_at), (doc, requested_at), (status, requested_at).
- **Knowledge registry** is in code, not in the DB: `KnowledgeRegistryEntry {docId, aliases[], docState, contentType, sourcePath}` (`agentKnowledgeService.ts:63-69`, built at l.491-503). Doc version is a content hash computed per request (l.564-566).
- **`messages.agent_send_key`** (`schema.ts:1652`) with partial unique index `idx_messages_agent_send_key ON (sender_id, agent_send_key) WHERE sender_type='agent' AND agent_send_key IS NOT NULL` (l.1700-1702). `createOrReplayAgentSend` (`services/agentSendReplayService.ts:56-150`) does `INSERT … ON CONFLICT DO NOTHING RETURNING`. When no row comes back, it selects the existing row and returns `replayed:true`, all in one transaction.
- **Agent API send body** (`AgentApiSendV2Body`, shared): `target`, `content`, `attachmentIds?`, `mentions?` (typed `{type,id,name}`), `idempotencyKey?`, `sendDraft?`, `continueAnyway?`, `draftReholdCount?`, `draftReplacedExisting?`, `seenUpToSeq?`, `freshnessContextMode?` (`inline|withheld`). Server handler docs: `internalAgentApi.ts:3164-3182`.
- **Send response**: `state: "sent"` (`messageId`, `recentUnread`, pending mention actions, `attention.driveByJoinedToPost`) or `state: "held"` (held messages, `seenUpToSeq`, `freshnessContextMode`) (`send.ts:127-143`).
- **Profile credential file** `~/.slock/profiles/<slug>/credential.json` (or `$RAFT_HOME/profiles/<slug>`): `{schemaVersion, serverUrl, agentId, agentName, serverId, credentialId, scopes[], apiKey, createdAt}` (`auth/env.ts:79-89`).
- **CLI local state files** (per agent): `consumed-seqs.json` `{targets: {<target>: {seq, readOrder}}, nextReadOrder}` (`_consumedSeqState.ts:23-40`), and the draft store (`_continueDraftState.ts`: content, attachmentIds, mentions, savedAt, reholdCount, seenUpToSeq).
- **Wiki workspace pack** `WikiWorkspacePack {protocolVersion:1, packId, files:[{relativePath, content, sha256, size}]}` (generated file; shape asserted in `wikiWorkspacePack.contract.test.ts:28-58`).

## 4. Flows

### F1. Managed agent runs a `raft` command (auth path through the daemon proxy)
1. Daemon, at spawn → `cliTransport.ts` (around l.642-667): if the server attached `agentCredentialKey`, it deletes any legacy `agent-token` file and calls `registerAgentCredentialProxy({agentId, launchId, serverUrl, apiKey, activeCapabilities})` (`agentCredentialProxy.ts:1672`). That call mints `sap_<32 random bytes>` and keeps `token → registration` in an in-memory Map. The token has no TTL. It stays valid for the life of the launch, until `unregisterAgentCredentialProxyForLaunch` deletes the Map entry, and it only works against the loopback proxy. "Short-lived" means launch-scoped, not time-limited. If the server did NOT attach `agentCredentialKey`, the daemon takes a legacy path instead: it writes `ctx.config.authToken || daemonApiKey` to an `agent-token` file (0600) and sets `SLOCK_AGENT_TOKEN_FILE` in the wrapper, with no proxy (l.668-670). Current CLIs reject legacy machine tokens (`LEGACY_MACHINE_UNSUPPORTED`).
2. Daemon writes the proxy token to `$SLOCK_HOME/agent-proxy-tokens/<agent>/<launch>.token` (0600). It then writes the `raft` and `slock` wrappers (0755). The wrapper unsets `RAFT_PROFILE*`, then execs node with `SLOCK_AGENT_ID`, `SLOCK_SERVER_URL`, `SLOCK_AGENT_PROXY_URL`, `SLOCK_AGENT_PROXY_TOKEN_FILE` and `SLOCK_AGENT_ACTIVE_CAPABILITIES` inlined (l.694-705). The raw key never enters the agent environment.
3. Agent runtime → shell: `raft message send --target "#x" <<'RAFTMSG' … RAFTMSG`.
4. CLI `main.ts` → `forwardManagedTransportIfNeeded` (re-exec into the current launch wrapper if a stale or global binary was picked) → Commander parse.
5. Command → `loadAgentContext` (`env.ts:224`) → `clientMode:"managed-runner"`, `serverUrl` = the proxy URL, `token` = the proxy token.
6. `ApiClient.request` → HTTP to `127.0.0.1:<port>/internal/agent-api/...` with `Bearer sap_…`.
7. Daemon proxy `handleProxyRequest` (`agentCredentialProxy.ts:411`): looks up the registration (401 if missing), rejects any target whose origin differs from the registered server (403 `agent_proxy_origin_mismatch`), strips `authorization`/host/hop-by-hop headers, sets `Authorization: Bearer sk_agent_*`, `X-Agent-Id`, the active-capabilities header and a daemon child `traceparent`.
8. Some routes are answered locally: `GET /runtime-version`, `GET /inbox` (local inbox projection), `POST /inbox/ack` (l.504-560). The others are forwarded.
9. Server `/internal/agent-api/*` → auth derives `req.actingAgentId` from the credential row (id-less surface) → `requireAgentCapability(route.capability)` → per-route contract validators (when the route registered them, or inside the handler) → handler.
10. Response flows back through the proxy. For `/send` (v1 path only; see Surprises), `/events`, `/history` and `/messages/:id/resolve` it is buffered so the inbox coordinator can mark messages as consumed (`shouldBufferJsonResponse` l.1547). This happens only when the registration has an `inboxCoordinator` and the response is JSON.

### F2. `raft message send` (freshness hold, drafts, no idempotency key)
1. CLI `handleMessageSend` (`send.ts:439`): rejects positional or `--content` text (`POSITIONAL_CONTENT_UNSUPPORTED`, `CONTENT_FLAG_UNSUPPORTED`) and reads stdin (`resolveSendContent`). Parses `--mention human|agent:<uuid>:<handle>` and checks each handle still appears in the body (`MENTION_NOT_IN_CONTENT`).
2. Loads any previous draft for (agent, target). If it had a body, prints a "draft replaced" warning to stderr.
3. Thread guard: if the agent's most recent read under this parent was a thread, it saves a draft and fails with `THREAD_CONTEXT_TARGET_CONFIRMATION_REQUIRED`, unless `--target-confirmed` is passed (`detectThreadContextParentSend` l.366).
4. Picks `seenUpToSeq` in priority order: (a) with `--send-draft`, the draft's stored `seenUpToSeq`; (b) on a normal send, the previous draft's `seenUpToSeq` (the boundary the server served on the last hold); (c) only if both are absent, the local consumed cursor for exactly this target (`getConsumedSeq`, l.575-584). Only `message read` advances that cursor. Passive wake/inbox notices and `message check` do not. If nothing is found the field is omitted. The server then uses boundary 0 (or the thread parent's seq for a cold thread) and holds if any counted message exists (see step 8).
5. Builds the body. It always includes `draftReholdCount` (a number), and that alone makes the server run the freshness gate (`requestedSendFreshness`, l.3620). It adds `freshnessContextMode:"withheld"` in reviewer-isolation mode, `sendDraft`/`continueAnyway` for `--send-draft [--anyway]`, or `draftReplacedExisting` otherwise. On a normal send (not `--send-draft`) it saves the outgoing body as a draft before the network call (`setSavedDraft`, l.608-617). A `--send-draft` send reuses the stored draft and does not rewrite it first.
6. POST `/internal/agent-api/v2/send` through the shared client (`agentApi.messages.sendV2`). The body has no `idempotencyKey`.
7. (Daemon proxy) `prepareAgentApiSideEffectForward` (l.1480) → `planAgentInboxSideEffect` (`agentInboxStateMachine.ts:118`): if the daemon holds pending unseen messages for the target it can reply with a local held envelope, otherwise it forwards with an adjusted `seenUpToSeq`. **Note:** this match is on the literal path `/internal/agent-api/send` (l.1429), and the CLI now calls `/v2/send`. See Surprises.
8. Server `handleAgentApiMessageSend` (`internalAgentApi.ts:3588`, one handler for both `messageSend` and `messageSendV2`, registered l.4161-4162). Steps: validate the body → reject `continue` (deprecated) and `--anyway` without `--send-draft` (400) → the freshness gate is enabled when `SLOCK_ATTESTED_SEND_MODE` is `on` (the default) or `force`, or when the server/agent is on the allowlist in `allowlist` mode. If the client asked for freshness but it is disabled, the server returns 403. It runs only if the request carries freshness fields or mode is `force` → resolve target (403/404 for forbidden, peer-not-found, self-dm) → freshness evaluation (l.3749+). Boundary = min(client `seenUpToSeq` or thread-parent fallback or 0, latest seq). It counts messages after the boundary, excluding the agent's own. Channels and DMs count "attention" messages for this agent (`countAgentAttentionMessagesAfterSeq`). Threads count all messages. Hold if count > 0 and not `continueAnyway`. On hold it returns `state:"held"` with the unseen messages. Otherwise it calls `messageService.broadcastAndDeliver` (l.4055). That call persists the message, emits over Socket.IO and delivers to agent inboxes. If a key is present it passes `agentSendKey` to get replay dedupe.
9. CLI on `held`: records the served `seenUpToSeq` as consumed, bumps `reholdCount` in the draft, prints the held context and the two recovery commands (`--send-draft`, `--send-draft --anyway`), and exits non-zero with `SEND_HELD_AS_DRAFT`, `effect:"draft_saved"`, `retryable:false`.
10. CLI on `sent`: clears the draft and prints `Message sent to <t>. Message ID: …` plus a thread reply hint and "New messages you may have missed". If any mentions were not delivered it reports `MENTION_DELIVERY_FAILED` with per-mention recovery commands and "Do not resend the queued message."
11. CLI on a failure after the draft was saved: `markSendFailureDraftSaved` (`send.ts:396-440`). The UNKNOWN / `retryable:false` / "do not resend" guidance applies only when the failure is transport-ambiguous: `fault_domain === "agent_api_transport"`, or a non-CliError exception. Other CLI errors (for example a clean HTTP 4xx) keep their original `retryable`. A reviewer-isolation send collapses any failure to a generic `SEND_FAILED` with the upstream detail withheld.

### F3. `raft manual get <topic>`
1. CLI `knowledge/get.ts` → `requireKnowledgeContexts(intent, reason)`. Both must pass `validateKnowledgeContext`: 12-500 chars, ≤4 lines, no URLs, no `sk_*`/Bearer/`token=` patterns, no fenced code, no raw `[target=… msg=` headers (`shared/knowledgeContext.ts:20-63`).
2. GET `/internal/agent-api/knowledge?topic=…&intent=…&reason=…` with `X-Raft-Client: cli` and `X-Raft-Client-Capabilities: manual-context-v1`.
3. Server `requireAgentCapability("knowledge")` → `handleAgentKnowledgeGet` (`agentKnowledge.ts:33`): source must be `cli` (dual-reads `X-Slock-Client`). Intent and reason are required only when the client advertised `manual-context-v1` (a rollout switch, l.450-460). Turn and trace ids come from query or header and must agree. `agentBelongsToServer` → 401 if the agent was deleted.
4. `resolveAgentKnowledgeDocWithDiscovery` (`agentKnowledgeService.ts:610`): exact alias match (case-insensitive) → `exact_id|alias`. On a miss it tries whole-token routes (`skill|skills → runtime`) → `token_route`.
5. `readKnowledgeContent` reads the file from `SLOCK_KNOWLEDGE_ROOT`, the cwd or `../..`, then runs `sanitizeAgentKnowledgeContent`, which strips `{/* … */}` editorial comments outside code fences. The version is the content sha256.
6. `recordAgentKnowledgeEvent` → INSERT `agent_knowledge_events` (status, resolution, latency, bytes, intent, reason).
7. 200 `{ok, docId, topicOrPath, docVersion, docState, contentType, content}`. The CLI writes `content` to stdout unchanged.
8. Miss: 404 `knowledge_not_found` with `indexTopic`, `suggestedTopicIds`, `candidates` (weak-score suggestions labelled as such) and a `suggested_next_action` holding the exact index command.

### F4. `raft manual search "<keywords>" [--scope recipes]`
1. Same validation. The server rejects non-Latin-script queries (`manualQueryNeedsEnglish`) with 404 `knowledge_language_unsupported` and logs `resolution:"language_gate"`.
2. `searchAgentKnowledgeDocsWithResolution` (l.642): reads all docs in scope once, builds the corpus vocabulary, and scores each entry. Exact hits on docId, alias or title identify a doc outright. Other scoring uses stemmed terms, stop words, a small synonym table, and edit-distance-1 fuzzy matching for terms of length ≥5, weighted per field (docId 80, title 75, alias 45, content 25). There is a relevance floor (min score 70 plus ≥50% multi-term coverage). Returns the top 3.
3. The response includes `matchedTerms` and `correctedTerms` so the agent can see why each result matched (`serializeKnowledgeSearch` l.411-427). An event is logged either way.

### F5. External agent onboarding (`raft agent login`) and self-hosted use
1. Human or agent → `raft agent login --server <url> --agent <id> --profile-slug <slug>`.
2. CLI → `/api/auth/device/authorize` → prints `verification_uri_complete` + user code → the human approves in the web UI → the CLI polls `/api/auth/device/token` every 5s (`login.ts:249-252`).
3. CLI → POST `/api/agents/:id/credentials` to mint `sk_agent_*` (l.382) → writes to a temp dir → atomic rename to `credential.json` 0600 (l.415-429) → whoami check against `/internal/agent-api/`.
4. Later calls use `raft --profile <slug> …` → `clientMode:"self-hosted-runner"` → direct HTTPS to the server with the real key.
5. Optional `raft --profile <slug> agent bridge` (`bridge.ts:383`): lifecycle `starting` → replay locally stored wake hints (`connected_replaying`) → fetch new hints since `lastSeenHintSeq` → for each hint append proofs `server_delivered` then `harness_accepted` to local JSONL, emit a handoff, run the wake adapter (`wake_injected`) → drain and forward activity → persist the session cursor → end in `handoff_pending` or `listening_idle`.

### F6. Wiki Agent workspace provisioning
1. Server `agentOrchestrator` start: if the agent's env has the wiki workspace flag, it sends `agent:start:wiki` with `wikiWorkspacePack` instead of `agent:start` (l.9873-9881).
2. Daemon writes the pack files (`AGENTS.md`, `CLAUDE.md`, skill files for both `.agents/` and `.claude/`) into the workspace. The ensure path replies `agent:workspace:wiki_ensured {packId, files}` and the server verifies it with `isCompleteWikiWorkspaceEnsureReceipt` (l.10260-10290).
3. The agent's skill (`ingest.md`) drives `raft wiki manifest` (take the ETag) → `raft wiki read` → `raft server info` → publish with `expectedEtag`. This is optimistic concurrency on the manifest.

## 5. State machines

**Send outcome / draft lifecycle (CLI-local, `send.ts`)**
- `no_draft` → (send attempt) → `draft_saved` (written before the network call)
- `draft_saved` → server `sent` → `no_draft` (cleared)
- `draft_saved` → server `held` → `draft_held(reholdCount+1, seenUpToSeq=served)` → either new content (replaces the draft, warns) or `--send-draft` (resend the stored copy) or `--send-draft --anyway` (`continueAnyway`, freshness bypass)
- `draft_saved` → thread guard → `awaiting_target_confirmation` → `--send-draft` or `--target-confirmed`
- `draft_saved` → transport failure → `UNKNOWN` (terminal from the CLI's view: `retryable:false`, no auto-resend)
- `sent` with undelivered mentions → `partial` (message `queued`, mentions `not_queued`)

**Daemon freshness decision** (`AgentProxyFreshnessDecision.decision`, `agentCredentialProxy.ts:121`): `forward` | `local_hold` | `syncing_hold` | `bypass` (continueAnyway). Inputs: pending unseen messages for the target, model-seen boundary, recent history (when no boundary exists).

**Manual event status**: `success` | `not_found` (with `resolution=language_gate` as a sub-case) | `denied` | `error`. `denied` is declared in the enum and schema, but neither route handler ever writes it. Requests rejected before resolution are not logged at all: 400s for bad source, topic, intent, reason, turn or trace, and the 401 for a deleted agent. So `agent_knowledge_events` records every lookup that reached resolution, not every call. Resolution branches: `exact_id` → `alias` → `token_route` (get). For search: `lexical` | `concept_expansion` | `typo_correction` | `mixed`.

**Doc state** (declared): `draft` → `published` → `deprecated` → `retired`. In practice every registry entry is `published` (`buildAgentKnowledgeRegistryEntry` l.1300).

**Capability check** (`getAgentCapabilityFailure`, `internalAgentApi.ts:746`): credential scope missing → 403 `capability_not_authorized`. Scope present, active-capabilities header present and non-empty, capability not in it → 501 `unsupported_capability`. Otherwise pass. The active set is a header supplied by the caller: the daemon proxy sets it for managed agents, and the CLI sends it only if `SLOCK_AGENT_ACTIVE_CAPABILITIES` is set. So it can only narrow what the scopes allow. It is not a security boundary.

**Server send freshness gate** (per request): `disabled` (mode off, or not on the allowlist; if the client asked for freshness → 403) | `skipped` (enabled but the request carried no freshness fields and mode ≠ `force`) | `evaluated → passed` | `evaluated → held` (newMessageCount > 0 and not continueAnyway). Boundary sources: `client_seen` | `thread_parent` | `none`.

**Agent CommsCore bridge lifecycle** (`bridge.ts:26-37`): `unbound`, `bound_stopped`, `starting`, `connected_replaying`, `listening_idle`, `handoff_pending`, `degraded_backoff`, `stopping`, `stopped`, `auth_revoked`. ## 6. Design patterns worth stealing

1. **Use the CLI as the tool interface, with one `Bash`-style tool.** Instead of registering N typed tools per runtime, the agent gets a shell command with `--help` as the spec. The daemon puts the wrapper first on PATH, so every runtime (Claude Code, Codex, Kimi SDK, Electron-hosted) gets the same surface. Raft files: `AGENTS.md` principles 1, 4 and 6, `systemPrompt.ts:84-88`, `cliTransport.ts`. Why it matters for you: in AgentCore you can give Claude one `run_command` tool plus a CLI binary in the container. You version the CLI instead of re-shipping tool schemas, and the same binary serves humans, scripts and Temporal activities. Raft keeps an MCP path only for server-gated third-party tools (`managedMcpTools/managedMcpCall`, capability `mcp`, `agentApiContract.ts:1803-1822`). Note that `mcp` is not in the daemon's default active set.
2. **Put the credential in a local proxy, not in the agent.** The agent's shell sees only a per-launch `sap_*` token file. The daemon swaps it for `sk_agent_*`, pins the origin, and can revoke a launch by deleting a Map entry (`unregisterAgentCredentialProxyForLaunch`). Files: `agentCredentialProxy.ts:411-500,1672-1727`. Why: a prompt-injected agent cannot exfiltrate a long-lived key. Your AgentCore sidecar or gateway can play the same role.
3. **One route contract table, three consumers.** `agentApiContract` (method, path, capability, zod request/response) drives server registration (`registerAgentApiRoute` adds `requireAgentCapability(route.capability)` automatically), CLI calls and SDK calls. Why: capability enforcement cannot be forgotten on a new route, and the client and server cannot drift.
4. **Capability = credential scope ∩ runner-session capability**, with different status codes (403 vs 501) so the agent can tell "you may never" apart from "this runtime can't". File: `internalAgentApi.ts:746-777`. Only the scope half is authoritative. The runner half is an optional header set by the daemon proxy and is skipped when absent.
5. **Handles at the agent boundary, UUIDs inside.** Agents pass `#channel`, `dm:@peer`, `#channel:shortid`. The server resolves them and applies membership checks (`AGENTS.md` "Agent-facing identity reference contract"). Why: LLMs mistype UUIDs, handles are checkable, and resolution becomes the authz point.
6. **Freshness-gated writes (optimistic concurrency for conversation).** Send and claim carry `seenUpToSeq`. If the target moved past what the agent read, the server returns `held` plus the missed messages, and the body is kept as a draft. Per-target cursors are never merged, and a missing cursor fails closed (`_consumedSeqState.ts` header). Why: this is how you stop multiplayer agents from replying to stale context. It works like an ETag for chat.
7. **Errors written for the agent to read.** Every failure carries `code`, `retryable`, `effect` (`draft_saved`, `message_queued`), `fault_domain` and a literal `next_action` command (`renderer.ts:79-127`, `main.ts:127-167`). Why: the model recovers without guessing, and `retryable:false` on ambiguous writes stops duplicate loops.
8. **Be honest about idempotency, and pin the gap with a test.** The server supports dedupe (`agentSendKey` partial unique index plus `createOrReplayAgentSend`), the SDK exposes `idempotencyKey`, but the CLI does not send one. The Manual says so, and `agentKnowledgeService.sendIdempotency.test.ts` fails the build if the Manual starts promising dedupe, or if `send.ts` gains a key without the doc being revisited. Why: docs for agents are part of the product surface, and a false "retries are safe" leads to double posts.
9. **Docs as an on-demand, instrumented tool (the Manual).** The system prompt stays short. Detail is pulled with `raft manual get|search`, which requires the agent to state `intent` and `reason`. Every lookup (hit, miss, resolution branch, bytes, latency) goes to `agent_knowledge_events`. Hand-added aliases follow a documented convention of using only observed miss strings (comments in `EXTRA_AGENT_KNOWLEDGE_ALIASES_BY_DOC_ID`, l.351-487: "exact observed shapes, verbatim… unobserved neighbors must stay visible in telemetry"). Code review enforces this, not code. Other aliases come from elsewhere: legacy RFC-era paths (e.g. `rfcs/020-slock-home`) and auto-generated bare `<class>/<slug>` aliases for every recipe in a whitelisted class (`RECIPE_STRIPPED_PREFIX_WHITELIST_CLASSES`, l.488-509). Those were a response to a recurring observed miss, but they are generated for every recipe, not added one at a time. Why: you get a feedback loop on what agents don't know. For a research orchestrator this is cheap RAG with analytics, and the intent/reason strings amount to a labelled dataset of agent confusion.
10. **Content tests on docs ("teeth").** Tests such as `agentKnowledgeService.runtimeSkills.test.ts`, `.taskClaimLock`, `.sendIdempotency` and `agentKnowledgeServedBodyLeak.test.ts` assert what docs must and must not say. Why: this catches regressions in agent behavior that come from doc edits.
11. **One source for the prompt and the manual page.** `raftCliGuide.ts` generates both the managed system prompt sections and `raft-cli-overview.md`, and a freshness test prevents drift.
12. **Content-addressed workspace packs for specialist agents.** The Wiki agent's `AGENTS.md`, `CLAUDE.md` and skills ship as a sha256-identified pack. The daemon returns a receipt that the server verifies against the expected pack. Why: reproducible agent configuration per role, auditable per launch.
13. **Recipes as a coordination-pattern library** (`manual/recipes/pattern/{shard-and-merge,coordinator-synthesis,discuss-then-assign,gate-chain,interview-fanout}.md`, `technique/task-claim-lock.md`: "the claim is the concurrency lock"). These are behavioral protocols delivered as retrievable docs, not hard-coded orchestration.

## 7. Surprises / sharp edges

- **"sendIdempotency" is a doc-honesty test, not a feature.** `agentKnowledgeService.sendIdempotency.test.ts` asserts that the Manual does not promise dedupe, and that `send.ts` contains no `idempotencyKey|agentSendKey`. CLI and daemon sends are not idempotent. Every retry makes a new message (`manual/agent-knowledge/message.md:177-178`).
- **The SDK can retry sends without requiring a key, but only if the caller opts in.** `createAgentApiMessageClient` defaults to `retry.attempts = 1`, meaning no retry. The raft-sdk `createRaftClient` also defaults to 1. A caller can raise it to at most 5. Retries happen only on fetch exceptions (no HTTP response), and they happen whether or not `idempotencyKey` is set (`shared/src/agentApiMessageClient.ts:147-215`, `raft-sdk/src/client.ts:149`). With `retry.attempts>1` and no key, a lost response can double-post (inferred from code).
- **The daemon freshness preflight matches only the v1 path.** `agentApiSideEffectAction` and `shouldBufferJsonResponse` compare against the literal `/internal/agent-api/send` (`agentCredentialProxy.ts:1429,1551,1582`), but `raft message send` calls `messages.sendV2` → `/internal/agent-api/v2/send` (`send.ts`, `agentApiContract.ts:1836`). So the local hold and consume logic appears not to run for CLI sends. The server-side freshness gate still applies to both route keys (`internalAgentApi.ts:3588`). **Verified at code level:** the CLI's `rewriteAgentCredentialPath` does not map `/v2/send` back to `/send`. `agentCredentialProxy.ts` has no mention of `v2`. No daemon test (`agentCredentialProxy.test.ts`, `proxy.test.ts`, `runnerApp.e2e.test.ts`) exercises `/v2/send`. The gap has four effects for a CLI send: (a) no `local_hold`/`syncing_hold` preflight, so the daemon's pending-unseen view is not consulted; (b) the response is not buffered, so the inbox coordinator does not consume held messages or advance its boundary with the sent `messageSeq`; (c) `routeFamilyForPath` (l.1022) does not classify it as `agent-api/send`, so transport-error traces are labelled differently; (d) `seenUpToSeq` is forwarded unadjusted. Task claim and update (`/tasks/claim`, `/tasks/update-status`) still match. The server gate remains the real protection.
- **Message bodies only come from stdin.** `--content` exists as a flag only to return an error.
- **The draft is saved before the POST**, so a crash leaves a recoverable draft. It also means a later send to the same target silently replaces the draft (a stderr warning is printed).
- **The Manual is file-backed and read on every request.** Search reads every doc in scope each time. There is no DB storage and no cache in the service (`searchAgentKnowledgeDocsWithResolution` l.656-668). The registry is a hard-coded path list, so a new `.md` file is invisible until it is added to `AGENT_KNOWLEDGE_SOURCE_PATHS`.
- **Intent/reason enforcement is gated by a client header** (`manual-context-v1`), so older CLIs get lenient validation. The new CLI enforces it locally too.
- **Search refuses non-English queries** outright and logs this separately (`language_gate`) so misses are not polluted.
- **`raft manual` has a legacy alias `raft knowledge`**, and `slock` is an alias of `raft`. Dual env names (`RAFT_*`/`SLOCK_*`) that disagree fail loudly (`PROFILE_ENV_CONFLICT`).
- **The Manual cannot tell an agent what skills it has.** There is no `raft skill` command. `skill`/`skills` token-route to the `runtime` doc, which is tested to say "A missing query path is not a missing capability".
- **The `raft-sdk` is only a distribution layer.** Workspace code must not import it (exports point at `dist/`). Logic belongs in `raft-shared` (`raft-sdk/DESIGN.md`). `bootstrapRaftCredential` never overwrites a stored credential with a different one.
- **The external `agent bridge` is local-file state** (JSONL proofs, wake hints, a lock file with stale-owner detection) under the profile dir. It requires a profile credential and refuses managed mode.
