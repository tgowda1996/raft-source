# 02 — Messages as durable first-class objects

All paths are relative to `/home/user/raft-source`. `S` = `packages/server/src`. `MS` = `S/services/messageService.ts`. `AO` = `S/services/agentOrchestrator.ts`. `IAA` = `S/routes/internalAgentApi.ts`.

## 1. What it is

Every message in Raft is a row in one Postgres `messages` table. A single global `bigserial seq` orders all messages (`S/db/schema.ts:1646-1648`). Channels, DMs, threads and joint channels are all rows in one `channels` table, told apart by a `type` column. A thread is simply a channel of type `thread` that points at its parent message (`schema.ts:1450-1453`). A send goes in a fixed order. First, Postgres commits the message together with its derived facts in one transaction: mentions, inbox facts, attachment links and the Slack outbox. After the commit, the server does three things: it pushes to browsers over Socket.IO (best effort), puts the message into a per-agent in-memory inbox that the machine daemon acks, and sends push notifications. Anything that misses a push can recover from the database by `seq`. Browsers do this with `sync:resume` and HTTP `/messages/sync`. Agents do it with resume catch-up reads above their per-channel ack cursor. So the realtime paths only make delivery faster. The database is the source of truth.

## 3. Data model

**`messages`** (`schema.ts:1646-1712`)
- `id uuid`, `seq bigserial` — one sequence for the whole table, so it orders messages across all servers ("server-global seq for reliable delivery", comment at `:1645`). Order within one channel comes from index `idx_messages_channel_seq (channel_id, seq)`.
- `channelId` → `channels.id` (cascade delete).
- `senderType ∈ {user, agent, external_projection}`, `senderId text`. System messages use `senderType='user', senderId='system'`, `messageType='system'` (`MS:2027-2033`).
- `agentSendKey` with partial unique index on `(sender_id, agent_send_key) where sender_type='agent'`. `randomId` with partial unique index on `(sender_id, random_id) where sender_type='user'` (`:1700-1705`). These two indexes are the idempotency boundary.
- `content`, `actionMetadata json` (forwarded bundles, action cards), `searchText` + generated `searchVector` tsvector with a GIN index.
- `threadId`: set only on the **parent** message and holds the thread channel's id. Replies live in the thread channel with `threadId = null` (comment `:1658-1665`; only writer is `channelService.syncParentMessageThreadId`, `channelService.ts:6445`).
- `task*` columns: dead storage since v1.4. The `tasks` table is authoritative (`:1666-1674`).

**`channels`** (`:1445`): `type ∈ {channel, private, joint, dm, thread}`, `parentMessageId`, `archivedAt`, `deletedAt`. Unique index `idx_channels_active_thread_parent` gives at most one live thread per parent message (`:1464`).

**Membership**: `channel_agents (channelId, agentId, role, authorityRevision)` `:1590`. `channel_humans` `:1605`. `thread_follows (threadChannelId, followerType, followerId, parentMessageId, reason ∈ {replied, authored, mentioned, manual}, doneAt, unfollowedAt)` `:5140`.

**DM identity**: `dm_channel_identities (channelId, kind ∈ {human_self, human_human, human_agent, agent_agent}, peerKey)` `:1475`. The comment says membership rows are mutable, so DM identity is stored separately with a sorted participant key. A per-pair advisory lock prevents duplicate DMs.

**Joint (cross-server)**: `joint_channels (canonicalChannelId, status)` `:1497` owns the canonical message stream. `joint_channel_servers (jointChannelId, serverId, localChannelId, role ∈ {host, participant}, status)` `:1510` holds one local projection channel per server. `joint_channel_invites` `:1526`. `channel_conversion_jobs` `:1551` is a leased, phased job that converts a normal channel into a joint one: `prepare → drop_task_identity → move_parent_messages → prepare_threads → move_thread_messages → verify → finalize → done`. Joint threads reuse the same `joint_channels` / `joint_channel_servers` tables with a canonical thread channel (`channelService.ts:2035-2075`).

**Mentions**: `message_mentions (messageId, messageSeq, channelId, targetType, targetId, handleAtSendTime, notifiableAtSend, notifiedAt/By/Action)`, unique on `(messageId, targetType, targetId)` `:5669`. The handle is frozen at send time.

**Mention delivery**: `mention_delivery_occurrences` `:5698`. The primary key is the `message_mentions.id`. It stores `deliveryPayload jsonb` (the exact `AgentMessage`), `state`, per-hop timestamps, a machine/launch/session identity snapshot, `version`, and `redriveCount`. CHECK constraints tie `state='acked'` to `ackedAt`, and `terminal_error` to both terminal columns.

**Inbox facts**: `inbox_notification_facts (receiverType, receiverId, kind, sourceChannelId, messageId, messageSeq, personalMention, unreadEligible)` `:3904`, unique per receiver+message. Also `user_channel_inbox_states` `:3830`, whose `doneAt` is cleared on every new message in the channel (`MS:1990-1995`), and `inbox_serving_rows` `:3962`.

**Read cursors**: `user_channel_read_cursors` `:3667` and `agent_channel_read_cursors` `:4155`, each with `lastReadSeq int4`, `lastReadSeq8 bigint` (a shadow column for the int8 migration), `readStateVersion`, and `lastAppliedAuthoritySeq`. Read mutations are queued in `read_mutations` / `read_mutation_tombstones` `:3753`, `:3808`.

**Reactions**: `message_reactions` PK `(messageId, reactorType, reactorId, emoji)` `:3272`. `message_reaction_discussion_versions (messageId, emoji, version)` `:3287`. `message_reaction_viewer_versions` `:3300`.

**Saved**: `user_saved (userId, messageId, serverId)` PK `(userId, messageId)` `:5241`.

**Attachments**: `attachments` `:4551`, linked to a message inside the send transaction (`linkAttachmentRowsToMessageWithExecutor`, `MS:2465`).

## 4. Flows

### Flow A — Human sends a message (web)
1. Web composer builds an optimistic draft with `randomId = "msg-<ms>-<seq>-<rand>"` (`packages/web/src/components/message/optimisticMessageDraft.ts:30`) and POSTs to `/messages` (`MessageInput.tsx:2025`).
2. `routes/messages.ts:1616 createHumanMessage` validates the body, content length, `canUserPostToChannel`, and quota/billing read-only gates, then calls `messageService.broadcastAndDeliver` (`:1683`).
3. `broadcastAndDeliver` (`MS:8065`) resolves the requested channel. For joint or joint-thread channels it maps to the canonical `storageChannelId` (`MS:8112-8121`). It runs `assertChannelNotArchived` (`:8148`), extracts mention handles, and **resolves mention targets before the write transaction** (`:8188-8213`).
4. Persist (`MS:8406` → `createOrReplayUserRandomSend`, `MS:2303`). In one transaction:
   a. Take the Slack outbound admission lock (`lockOrdinaryMessageExternalDeliveryAdmission`).
   b. `INSERT messages ... ON CONFLICT DO NOTHING RETURNING`. Postgres allocates `seq` here.
   c. If the insert returned no row, this is a replay. Load the existing row by `(senderId, randomId)`. If `channelId` or the forward digest differs, throw `UserRandomIdConflictError` (HTTP 409). Content is **not** compared. Otherwise return the original row and its original target-visible mention facts (read back from `message_mentions`); `resolvedMentions` / `pendingMentionActions` come back empty on replay. Almost nothing new is written — the one exception is that attachment ids in the retry are re-linked to the original message in `"replay"` mode (`MS:2415-2430`).
   d. On a winning insert: clear `user_channel_inbox_states.doneAt` for the channel, link attachments, then `finalizeNewChatMessageInTransaction` (`MS:2134`) inserts `message_mentions` (+ `mention_delivery_occurrences` rows, `insertMentionRowsWithOccurrenceRecords` `MS:7649`), `inbox_notification_facts` (`recordInboxFactsForPersistedMessage` `MS:1284`), and the Slack outbound delivery row (`maybeEnqueueOrdinaryMessageExternalDelivery`).
   e. **Third persistence path (no key).** CLI, daemon and any other sender without a `randomId`/`agentSendKey` go through `persistDirectSend` inside `messages.direct_send_transaction` (`MS:8438-8513`): same admission lock, plain insert, attachment link, `finalizeNewChatMessageInTransaction`. So atomicity does not depend on having an idempotency key — only replay-safety does. (A non-transactional `direct_send_insert` branch exists only when unit tests inject a `MessageServiceDeps` override, `useAtomicMessageTransaction = messageServiceDepsOverride === null`, `MS:8105`.)
   f. The mention rows written here already include the `mention_delivery_occurrences` row in state `recorded` for every notifiable agent mention — **but with `deliveryPayload = NULL`**. The payload is attached later, after commit (Flow C step 4). See the two-phase note there.
5. COMMIT. The message and all derived facts are now durable together.
6. If `asTask`: `ensureTaskForMessage` creates the canonical task (idempotent) (`MS:8535`).
7. Socket fan-out: `emitPersistedMessageToFrontend` (`MS:8700` → `MS:2534`), wrapped in `emitFrontendSocketBestEffort` (`MS:2501`). A socket error is recorded as a trace event (`message_pipeline.frontend_socket_emit.degraded`, `failure_policy: "continue_from_persisted_state"`) and does **not** fail the HTTP request. Note the emit runs **even on a replay** — it happens before the replay early-return, so clients dedupe by message id.
8. If replayed: return here (`MS:8734`). No sender read, agent delivery, or push is repeated.
9. Advance the sender's own read cursor (`markRead` / `markAgentLegacyRead`, `MS:8739`) and emit the read receipt asynchronously (`scheduleSenderReadReceipt`, `MS:506`).
10. Agent delivery (Flow C) is started without waiting (`MS:9068-9235`).
11. Push: `buildPushTargets` → `persistNativeNotificationIntents` → `sendPushNotifications` (web push, not awaited) + a `notification:push` socket emit (`MS:9256-9316`).
12. The HTTP response returns the enriched message plus sender-only `pendingMentionActions` / `unresolvedMentionHandles` (`routes/messages.ts:1697-1712`).

### Flow B — Socket.IO fan-out (inside step 7)
1. On connect (`S/socket/index.ts`) the socket joins `user:<id>`, `server:<id>`, `user-server` rooms and **every** channel/DM room the user can see (`listChannels` + `listDMChannels`). It then emits `rooms:joined`.
2. Plain channel/private: `io.to("channel:<id>").emit("message:new", payload)` (`MS:2851`).
3. DM: first `io.in(user-server room).socketsJoin("channel:<dm>")` for every human, so a brand-new DM still reaches them. Then `message:new` to the channel room, plus `dm:new` to the channel room and to each `user:<id>` (`MS:2798-2806`, `:2876-2882`).
4. Thread: record thread follows (the sender as `replied`, the parent author as `authored`), mark the sender's read, clear thread "done" for everyone (`MS:2733-2771`). Human followers are added to the thread room with `socketsJoin`. If the parent is a public channel, emit to `channel:<thread>`. If the parent is private or a DM, emit to each follower's `user:<id>` room (`MS:2826-2842`). Then emit `thread:updated` (reply count, `latestReply`, `syncCoreReplyWindow`) to the parent channel room, or to each parent member's user room for private/DM parents (`MS:2884-2902`).
5. Joint channel: for each active projection, call `updateMaxSeq(projection.serverId)`, rewrite `channelId` to that server's `localChannelId`, and emit to `channel:<localChannelId>` (`MS:2590-2617`). Joint threads do the same per local thread, targeted at followers (`MS:2620-2718`).
6. `updateMaxSeq(serverId, seq)` updates an in-process map and mirrors it to Redis without waiting (`MS:6684-6691`).
7. Multiple replicas: the Socket.IO Redis adapter carries the emits (`socket/index.ts`, `createAdapter`).

### Flow C — Delivery to agents (inside step 10)
1. Choose the audience. For a thread: the agent followers, from persisted facts (`resolveThreadAgentDeliveryCandidates`). Otherwise: `channel_agents` for the channel. In a public `channel`, agents who are not members but were @mentioned in a target-visible way are added (`MS:9081-9086`). A thread @mention of a parent-channel member agent creates a `thread_follows` row with reason `mentioned` (`MS:8960-9010`).
2. Remove the sender itself and agents who muted the channel. Personal mentions and the task assignee pierce the mute (`MS:9087-9100`).
3. Build one `AgentMessage` payload per agent. It carries channel name/type, `sender_name`, `seq`, `message_id`, `mentioned`, parent info for threads, attachments, and `thread_join_context` for mentioned agents (`MS:9150-9185`). DM `channel_name` is the peer's handle, not the stored channel name.
4. **Record before delivering (two-phase).** Phase 1 is inside the send transaction: `insertMentionRowsWithOccurrenceRecords` (`MS:7649-7685`) writes the occurrence row (`state='recorded'`, payload NULL) atomically with the `message_mentions` row. Phase 2 is post-commit but before any send: `ensureAgentMentionDeliveryOccurrencesForAgents` (`MS:9197`) upserts the built `AgentMessage` into `deliveryPayload` with `coalesce(existing, new)` (`mentionDeliveryOccurrenceService.ts:161-172`). Comment at `:9188-9191`: "recorded but never delivered" is recoverable; "delivered but never recorded" is not. **Declared degradation:** if phase 2 throws, the server still delivers, emits `message_pipeline.mention_occurrence.persist_degraded {recoverable:false}`, and that mention can never be redriven, because recovery listings filter on `deliveryPayload IS NOT NULL` (`MS:9203-9222`). Rule: a bookkeeping write must never suppress the thing it records.
5. For each agent: `agentOrchestrator.deliverMessage(agentId, payload, {mentionDeliveryOccurrenceId})` (`MS:9227`, not awaited, tracked for drain).
6. `deliverMessage` (`AO:10920`) checks:
   - the `inbox:receive` scope. If it has been revoked, the message is `dropped/passive_scope_revoked` and **is not queued for later**.
   - target access.
   - the runtime type. External runtimes get the local inbox plus an `external-inbox-delivered` event and a cross-replica wake signal (`AO:10955-10977`).
   - Otherwise `planWakeAction`: control-gated agents (for example, mid-migration) get inbox-only. Stopped or sleeping agents get a wake action. Running agents get `applyDirectDelivery`.
7. `applyDirectDelivery` (`AO:11120`) runs in this exact order: (i) for a tracked mention, a CAS `recorded → server_decided` that also snapshots `(machineId, launchId, sessionId)` into the row; if the CAS loses, the delivery is `dropped/agent_state_changed` (`AO:11128-11151`); if the agent has no launch/session identity yet it returns `queued/replayable_inbox` and the caller falls back to `abandonMentionDeliveryWithoutInstrumentation`. (ii) Put the message in the replayable in-memory inbox — **possibly on another replica**: when the machine's socket is owned by a different server replica, the inbox write is routed cross-replica through the replica state store (`routeInboxDeliveryCrossReplica`); the comment warns pub/sub publication is only a route signal, not proof the other replica accepted it. The comment explains the inbox-before-send order: the daemon can ack immediately from `ws.send`, so the inbox must exist first. Transient deliveries (reminders) skip the inbox because they have no `messages.seq`. (iii) Send `{type:"agent:deliver", agentId, message, seq, deliveryId, mentionDelivery}` to the machine socket.
7b. **Server-side ack retry (missed by earlier draft).** Every `agent:deliver` is tracked in `pendingAgentDeliveryAcks`; if no ack arrives in `AGENT_DELIVERY_ACK_TIMEOUT_MS = 5_000` it is re-sent, up to `AGENT_DELIVERY_ACK_MAX_ATTEMPTS = 24` (~2 min), then logged as `ack_retry_exhausted` and dropped (`AO:2104-2105`, `AO:8882-8925`, `AO:9096-9125`). When the machine is offline the entry is *parked* (timer stopped) and retried on machine `ready`/`register`. This map is in memory; tracked mentions are excluded from it on reconnect because they are rebuilt from Postgres instead (below).
8. Daemon (`packages/daemon/src/core.ts:3662`): for tracked mentions it first checks that the frame's `machineId/occurrenceId/messageId` match its own; a mismatch is reported back as terminal `IDENTITY_DRIFT` or `INSTRUMENT_FAILED`. If the agent is still starting, buffer the delivery. Otherwise `agentManager.deliverMessage(...)`. On accept, send `agent:deliver:ack {seq, deliveryId}` (`:3395`). Tracked mentions instead send `agent:delivery:transition` for `daemon_received` / `daemon_pending` / `daemon_drained`, and send the ack only at the end (`onMentionAck`).
9. Server ack handler (`AO:7522-7600`): check the mention identity (a drift makes it terminal), `recordMentionDeliveryAck`, then `acknowledgeDeliveredMessages(agentId, [seq])`, which removes the entry from the in-memory inbox. **It does not move any durable cursor** — `agent_channel_read_cursors` is advanced by read/model-seen paths (and by `/events` as a legacy fallback), not by the daemon ack.
10. **Automatic durable mention recovery (missed by earlier draft).** On machine `ready` (`AO:6471`) and on each `agent:session` that persists an active session with a `launchId` (`AO:7192`), the server calls `recoverDurableMentionDeliveriesForMachine/ForAgent` (`AO:8958-9040`): list un-acked occurrences with a payload; if the row's identity snapshot differs from the agent's current `(machine, launch, session)` mark it `IDENTITY_DRIFT`; if still `recorded`, CAS it to `server_decided`; skip `daemon_drained`; otherwise re-enqueue to the inbox and re-send with ack retry. So redrive is mostly automatic; the operator path (`POST /servers/:id/machines/:machineId/agents/:agentId/diagnostic/mention-delivery/:messageId/redrive`, `routes/servers.ts:3892` → `AO.redriveMentionDelivery` `AO:11066`) is a one-shot manual extra.

### Flow D — Agent sends a message (CLI → agent API)
1. `raft message send` → `POST /internal/agent-api/send` (`handleAgentApiMessageSend`, `IAA:3591`). The body may include `idempotencyKey` and `seenUpToSeq`.
   Before the request, the **CLI** (`packages/cli/src/commands/message/send.ts:474-600`) saves the draft **locally** (per-agent private state file, not on the server), and attaches `seenUpToSeq` from its own per-target "consumed seq" file (`_consumedSeqState.ts`). That cursor is written only by `raft message read` (a contiguous history slice) and by a previous held response — never by `message check` or wake notices, and never shared across targets even though `seq` is global. No local cursor → `seenUpToSeq` omitted.
2. Freshness gate (`IAA:3747-3830`). **When it runs:** enabled by `SLOCK_ATTESTED_SEND_MODE` (default `"on"`; also `force` or an `allowlist` of server/agent ids, `IAA:1041-1052`) **and** the request opts in (`seenUpToSeq`, `draftReholdCount`, `sendDraft`, etc.) or mode is `force` (`IAA:3621-3683`). The CLI always sends `draftReholdCount`, so CLI sends are always gated; a raw API client that sends none of those fields skips the gate. It computes the latest anchor, excluding the agent's own messages: attention facts for channels/DMs, raw messages for threads. The "attested boundary" is `min(seenUpToSeq, latest)`; **an absent `seenUpToSeq` counts as 0** (or the thread parent's seq for a cold thread), so a first send into a channel the agent never `read` is held — fail-closed by design. If newer messages exist and `--anyway` was not given, it returns **200 `state:"held"`** (`decision:"syncing_hold"`) with the new messages, a new `seenUpToSeq`, and `continueAnywaySuggested: true` after 3 re-holds. The CLI records the new boundary and bumps the local draft's `reholdCount`. The agent re-reads, then sends with `--send-draft` (re-checked; may re-hold) or `--send-draft --anyway` (`--anyway` without `--send-draft` is a 400). A "reviewer isolation" mode (`freshnessContextMode:"withheld"`) holds without showing the new messages.
3. Otherwise `broadcastAndDeliver(..., agentSendKey: idempotencyKey)` (`IAA:4056-4068`). With a key this goes through `createOrReplayAgentSend` (insert-or-replay with `beforeInsert` / `onInserted` callbacks inside the transaction); without a key (the CLI case) it goes through the ordinary `direct_send_transaction`. Then Flows B and C. The sending agent is excluded from delivery. Note that the agent replay path, unlike the user path, **does not compare channel or content** on a key collision — it silently returns the original message — and it returns the *freshly resolved* `resolvedMentions` rather than frozen ones (`agentSendReplayService.ts:120-151`, `MS:8388-8398`).
4. The same route runs the send-freshness bookkeeping in `attested_send_events`.

### Flow E — Browser catch-up after disconnect
1. On reconnect, the server auto-joins rooms and then emits `rooms:joined`.
2. Web `roomsJoined` (`socketBridge.ts:913`) sends `sync:resume {lastSeq}` and also calls `syncVisibleScopes`, `loadChannels`, `loadUnreadCounts`, `loadInboxReset`.
3. Server `sync:resume` → `syncMessages(lastSeq, undefined, 500, serverId, _, userId)`. This is a single SQL query: `seq > lastSeq`, the server's non-deleted channels, and a visibility predicate (public / member of private or DM / follows the thread and can read its parent), ordered by seq, `LIMIT 500` (`MS:6489-6620`).
   (Server ignores `sync:resume` when `lastSeq <= 0`, and on a query error it logs and sends **no** response — the client relies on the other reload calls in step 2. `socket/index.ts:244-269`, `RESUME_LIMIT = 500`.)
4. The server replies `sync:resume:response {messages, currentSeq, hasMore}`. The client merges the messages and sets `lastSeq = max`. If `hasMore`, it falls back to reloading unread counts and visible scopes (`socketBridge.ts:935-980`).
5. Heartbeat: every 15s the server emits `{seq: getMaxSeq(serverId), ts}`. `getMaxSeq` reads an in-process per-workspace map that is only as fresh as the last local `updateMaxSeq` or the 5s Redis pull (`MAX_SEQ_REDIS_SYNC_INTERVAL_MS`, `MS:6628-6660`), so a quiet replica can lag another replica's writes by up to ~5s plus the 15s tick. If `seq > lastSeq`, the client re-syncs visible scopes (`socketBridge.ts:1143-1149`). If there is no heartbeat for 90s and no events for 120s, the client forces a reconnect. `lastSeq` is saved to `sessionStorage` on pagehide (`:1195`).
6. HTTP fallback: `GET /messages/sync?since_seq=&channel_id=` (`routes/messages.ts:2089`) uses the same query. For joint channels it reads the canonical channel and re-labels results with the local channel id.

### Flow F — Agent catch-up
- **Managed agents (daemon)**: when an agent resumes a session without a wake message, `AO:9803` calls `getAgentResumeCatchupMessages` (`MS:4008`). It selects unread rows with `messages.seq > COALESCE(agent_channel_read_cursors.last_read_seq,0)` from joined channels, excluding the agent's own messages. It sorts first by "piercing" rows (DM, assigned task, personal mention) and then by recency. It **does not move any cursor**. The daemon decides what the model actually saw.
- **External agents**: `GET /internal/agent-api/events?since=` (`IAA:3204`). It first rebuilds the in-memory inbox from durable ack cursors (`rebuildExternalAgentPendingFromAckCursors`, `MS:4274`), because a server restart empties the inbox. It then drains without blocking, discards entries the agent can no longer access, refreshes task projections, **acks exactly the returned batch**, and returns `last_seen_seq`.

### Flow G — Thread creation
1. The first reply is sent to target `#chan:<8-char short id>`. `channelService.getOrCreateThread` (`channelService.ts:6464`) inserts a `channels` row (`type='thread'`, `name=thread-<8>`, `parentMessageId`) with `ON CONFLICT DO NOTHING`. The unique index `idx_channels_active_thread_parent` settles races, and the loser reads back the canonical thread.
2. `syncParentMessageThreadId` stamps `messages.threadId` on the parent.
3. Opening a thread never creates a follow. Follows are written only by a reply, an authored parent, a mention, or a manual follow (`channelService.ts:6456-6462`).

### Flow H — Reaction
1. `POST /messages/:id/reactions` (`routes/messages.ts:1942`) or agent `messageReactionAdd` (`IAA:2500`) → `mutateMessageReaction` (`messageReactionService.ts:237`). In one transaction: insert `ON CONFLICT DO NOTHING` (or delete); if something changed, bump the `(message, emoji)` discussion version; if the aggregate went from 0 to 1 or 1 to 0, enqueue an external (Slack) reaction transition; for users, bump the viewer version.
2. Emit `message:updated` (producer ids in `messageRealtimeProducerRegistry.ts:107-152`).

## 5. State machines

**Mention delivery occurrence** (`schema.ts:5713-5723`, `mentionDeliveryOccurrenceService.ts`)
- (created) → `recorded`, inside the message transaction, payload NULL; payload filled post-commit (see Flow C step 4).
- `recorded` → `server_decided` (CAS `where state='recorded' and serverDecidedAt is null`, `:174-230`, in `applyDirectDelivery` and in automatic recovery). This write also freezes the identity snapshot `(machineId, launchId, sessionId)` and (re)writes the payload. If it was already decided with the same identity + message id, the existing row is returned (idempotent); if the row is `acked`/`terminal_error` it returns null so the caller does not re-deliver (a comment documents a double-delivery bug this closed).
- `server_decided` → `daemon_received` → (`daemon_pending` if the agent was busy; `deliveryPath='busy'`, `pendingCoalescedCount++` when coalesced) → `daemon_drained` (`:234-269`). The daemon transitions are **monotonic `CASE` updates**: `daemon_received` applies only from `server_decided`, `daemon_pending` only from `server_decided|daemon_received`, and `daemon_drained` is set from any live state (so `daemon_received` / `daemon_pending` are optional hops). Every daemon write is guarded by the identity snapshot (`identityWhere`), so a stale session cannot move the row. `deliveryPath` ends as `immediate` or `busy`.
- `daemon_drained` → `acked` (requires `daemonDrainedAt IS NOT NULL`, `:271-306`)
- any non-terminal state → `terminal_error`, with codes `IDENTITY_UNKNOWN | IDENTITY_DRIFT | QUOTA_LIMITED | DELIVERY_REJECTED | UNSUPPORTED_DELIVERY_PATH | INSTRUMENT_FAILED`. `recorded` → `terminal_error` via `abandonMentionDeliveryWithoutInstrumentation` when the daemon never set up a session identity. The message is then delivered untracked, and only the caller that wins the CAS sends it (`AO:10999-11037`).
- Recovery is **automatic first**: on machine `ready` and on agent session start the server re-sends every recoverable occurrence (Flow C step 10). Recoverable listings: `server_decided | daemon_received | daemon_pending` per machine, plus `recorded` per agent; all require `deliveryPayload IS NOT NULL` (`:357-380`). Identity mismatch at recovery → `terminal_error/IDENTITY_DRIFT`.
- Manual redrive: an operator `POST .../mention-delivery/:messageId/redrive` runs `claimMentionDeliveryRedrive` (CAS on `version`, identity snapshot, `redriveCount = 0`), which re-enqueues and re-sends (`AO:11066-11118`). Outcomes: `REDRIVE_QUEUED | CAS_MISMATCH | IDENTITY_DRIFT | IDENTITY_UNKNOWN`. **`redriveCount` is a one-shot latch, not a counter** — the `redriveCount = 0` predicate means it can only ever be 0 or 1 (comment at `:423-434`).
- The table itself never runs a retry loop (schema comment `:5695-5697`); retries come from the in-memory ack-retry map plus the reconnect-time recovery.
- Diagnostic view `evaluateMentionDeliveryOccurrence` (`:101-159`) reports `ACKED | TERMINAL_ERROR | BROKEN_HOP(hop) | INSTRUMENT_FAILED(missingReceipt)`.

**Agent delivery receipt** (`AO:1410-1430`): `queued{external_inbox | control_gate_inbox | wake_accepted | replayable_inbox | direct_dispatch}` or `dropped{agent_unavailable | passive_scope_revoked | target_access_changed | transient_delivery_unsupported | reset_in_progress | wake_failed | wake_suppressed | cross_replica_receipt_unavailable | agent_state_changed}`. The comment says `queued` never proves the daemon or model consumed the message.

**Read mutation** (`readMutationSequencer.ts:38-45`): `admitted → executing → applied | retired_no_effect`, with terminal reasons `effect_applied | already_satisfied | authorization_revoked | done_frontier_beyond_latest`. Kinds: `row_read | row_unread | channel_read_all | global_read_all | done`.

**Thread follow** (`thread_follows`): absent → active (`reason` replied/authored/mentioned/manual) → `doneAt` set (done) → cleared by a new reply (`clearThreadDoneForAll`) ; active → `unfollowedAt` set → reactivated by a direct @mention (`reactivateUnfollowed`, `planDirectMentionThreadFollow` `MS:799`).

**Channel**: active → `archivedAt` (writes rejected by `assertChannelNotArchived`) → unarchived; any → `deletedAt` (soft delete).

**Joint channel**: `joint_channels.status active|closed`; per-server projection `active|disconnected`; invite `pending → accepted|declined|revoked|expired`; conversion job `pending → running → done|failed|canceled` with the phases listed in section 3.

**Held send (agent)**: draft (saved in the CLI's local private state, not on the server) → `held` (200, new messages shown, CLI bumps `reholdCount` and records the new `seenUpToSeq`) → `--send-draft` (re-checked: commit or re-hold; `continueAnywaySuggested` after 3 re-holds) or `--send-draft --anyway` (commit anyway). Sending new content to the same target replaces the draft. Server-side ledger values: `ContinueResult = committed | committed_anyway | reheld | replaced | expired | no_draft`, events `gate_triggered | continue | silence | e1_exempt` in `attested_send_events` (`attestedSendService.ts:17-19`).

## 6. Design patterns worth stealing

1. **Client-minted idempotency key with a partial unique index plus "insert-or-read-back" in one transaction.** `ON CONFLICT DO NOTHING RETURNING`. On conflict, read the winner and check the payload still matches (channel, forward digest), otherwise return 409 (`MS:2303-2410`, `agentSendReplayService.ts:56-151`, indexes at `schema.ts:1700-1705`). A replay returns the facts **frozen at the first send** and does not re-resolve mentions against current membership (`MS:2415-2420`). *Why:* retries from flaky networks or retrying workers (Temporal activities!) become safe, and the second response is byte-identical to the first.
2. **Commit all derived facts with the message; treat realtime as a post-commit acceleration.** Mentions, inbox facts, attachment links and the Slack outbox all share the message transaction (`finalizeNewChatMessageInTransaction`, `MS:2134`). Socket emits are wrapped so a failure cannot fail the send (`MS:2501-2530`). *Why:* there is never a message without its notifications, and never a notification for a message that does not exist.
3. **Transactional outbox for external systems.** The Slack delivery row is enqueued inside the message transaction (`maybeEnqueueOrdinaryMessageExternalDelivery`, `MS:2246`), and so are reaction transitions (`messageReactionService.ts:276-289`). *Why:* the same fix applies to webhooks and Temporal signal dispatch.
4. **"Record before deliver" for anything you might need to redrive.** The occurrence row with the full payload is written before any send (`MS:9186-9215`). The comment gives the one-sided rule: a record with no delivery can be recovered; a delivery with no record cannot.
5. **One monotonic seq as the catch-up cursor for every consumer.** Browsers use `lastSeq` + `sync:resume` + heartbeat max-seq. Agents use `agent_channel_read_cursors.last_read_seq`. Everything is `WHERE seq > cursor ORDER BY seq`. *Why:* one number answers "what did I miss". The heartbeat turns a lost push into at most a 15s delay.
6. **Model everything as a channel.** DMs, threads, and joint projections are rows in `channels`, so one message table, one membership model, and one catch-up query cover all of them. A thread is a channel with `parentMessageId`.
7. **Canonical store + per-tenant projections for cross-org sharing.** A joint channel keeps one canonical message stream. Each server has a local projection channel with its own membership, read cursors, and name. Payloads are re-labelled with `localChannelId` on the way out (`MS:2590-2617`, `projectJointMessagesToLocalChannel` `MS:6430`). *Why:* this is a clean model for "multiplayer across teams or orgs" without merging tenants.
8. **Separate visibility from delivery/wake.** Channel members can read everything. Agent delivery goes only to members and followers. A mention to a non-member becomes a sender-side notify/add action instead of an automatic delivery (`MS:9072-9086`, `manual/agent-knowledge/mention.md:140-150`). *Why:* agents are not woken by noise, and a mention cannot be used to pull an agent into a room it has no access to.
9. **Optimistic concurrency for agents ("freshness gate").** An agent's send is held if messages it has not seen arrived after its `seenUpToSeq` (`IAA:3747-3830`). The boundary is attested by the client from what it actually printed into the model's context (`raft message read`), and a missing boundary fails closed (hold). *Why:* this directly stops the multi-agent problem of replying to a stale context.
10. **Durable facts and a volatile inbox, split on purpose.** The per-agent inbox is an in-memory queue acked by seq (`AO:676`, `AO:11681`). After a restart it is rebuilt from Postgres: for external runtimes, `/events` refills it from `agent_channel_read_cursors` (`MS:4274`, `IAA:3228-3233`); for managed (daemon) agents, missed messages come back as resume catch-up on session start (`MS:4008`) and tracked @mentions come back from `mention_delivery_occurrences` on machine ready (`AO:8958`). Delivery is also retried in memory every 5s up to 24 times until the daemon acks. *Why:* the hot path stays cheap and correctness still comes from Postgres.
11. **A closed registry of realtime producers.** Every `message:new` / `message:updated` call site has a comment marker. The registry pins each one's audience and allowed payload keys, and a test checks that markers and call sites match one to one (`messageRealtimeProducerRegistry.ts:1-20`). Storage-only columns (`agentSendKey`, `searchText`) are stripped by an allowlisted projection (`messageRealtimeEvents.ts:44-92`).

## 7. Surprises / sharp edges

- **Message content has no edit or delete path.** `routes/messages.ts` has no PATCH or DELETE for message content (its routes are listed at `:680-2089`). No service runs `update(messages)` on `content` either (grep over `services/`, `routes/`). `message:updated` is only emitted for reactions, task projections, action cards, and attachment-comment scrubs. The manual claims that "server routes exist" for edit/delete (`manual/agent-knowledge/message.md`, "What it CAN'T do"). In this fork, messages are effectively append-only (verified by grep; I did not check older branches).
- **Agent sends are not idempotent in practice.** The server supports `agentSendKey`, but the CLI and daemon never send `idempotencyKey` for `message send` (re-verified: the only CLI hits for "idempotency" are in `commands/integration/invocationStoreV1.ts`, an unrelated integration-invocation store). The manual says so (`message.md`, Gotchas). Web sends do use `randomId`. Even when a key *is* sent, the agent replay path returns the original row without checking that channel/content match, whereas the user path 409s on a channel mismatch.
- **The freshness gate is effectively always on for the CLI, and fail-closed.** Because the CLI always sends `draftReholdCount`, every CLI send is gated when `SLOCK_ATTESTED_SEND_MODE` is `on` (the default). A first send into a target the agent never ran `raft message read` on has no `seenUpToSeq`, so it is held until the agent reads. A raw API client that omits all freshness fields bypasses the gate unless the mode is `force`.
- **`messages.seq` is one global bigserial, but read cursors are `int4`.** There is a `seqHeadroomTripwire.ts` that warns at 50% and 80% of 2^31, and an unfinished int8 shadow column `lastReadSeq8`. `sync-core` uses `bigint` specifically so that values above 2^53 stay exact (`types.ts:40-52`).
- **Seq is allocated at insert, not at commit.** A transaction that commits later can have a lower seq than one that is already visible (inferred from standard Postgres sequence behaviour). A client that sets `lastSeq = max(seen)` could skip it. `syncVisibleScopes` and heartbeat-driven re-sync appear to be the safety net (inferred). `prepareSystemMessageForOrderedDelivery` reserves a seq with `nextval` before persisting (`MS:2009-2054`).
- **The agent inbox lives in memory** (`agentInboxes = new Map`, `AO:2028`). Durability comes from the cursor-based rebuilds, not from the queue. A `passive_scope_revoked` drop is never re-queued, on purpose.
- **Ack is not "model saw it", and it moves no durable cursor.** The daemon ack only means the agent manager accepted the message; the server just removes the entry from the in-memory inbox. `/events` additionally advances the durable legacy ack checkpoint only for daemons that do not advertise the model-seen-boundary capability (`IAA:3339-3349`). The code keeps delivery ack, the legacy read cursor, and a `seenUpToSeq` "model-seen boundary" apart, and freshness uses only the last (`IAA:3764-3770`, `:3339-3358`).
- **`messages.threadId` means the opposite of what its name suggests.** It is set on the parent and holds the thread channel id. Replies have `threadId = null` (`schema.ts:1658-1665`).
- **Joint thread replies skip the ordinary agent delivery path.** `broadcastAndDeliver` returns early with `reason: "joint_thread_projection"` (`MS:8766`); `handleJointThreadPostBroadcastSideEffects` handles them instead (`MS:7028`).
- **Mention rendering and mention delivery use two different code-span parsers** (web `MessageItem.tsx` `protectCode` vs `shared/src/slockRefs.ts`), so they can disagree at the edges (`message.md` header notes).
- **In private or joint channels, a mention of a real non-member resolves to nobody and leaves no durable record.** Only the sender sees a warning at send time (`mention.md:243-247`).
- **The sender's description is assembled at read time**, so rendered agent-facing messages change whenever a profile description changes (`message.md` Gotchas).
- **`packages/raft-event-buffer` has nothing to do with message catch-up.** It is a bounded, memory-only batching buffer that exports trace rows (`TRACE_EVENT_ROW_V2`, `core.ts:1-80`). **`sync-core`** is a pure seq/epoch sync state machine (contiguous vs sparse density, difference vs snapshot repair, violation ring buffer). It is used for Activity/inbox and read-state (`web/src/store/readStateSync.ts`, `activityPanel/*`, `server activitySyncService.ts`), for thread reply windows (`syncCoreReplyWindow`), and — **correction** — behind the `sync_core_messages_v0` / normalized-message-v2 feature flags it also ingests live `message:new` frames on the web for dedupe/folding (`web/src/store/messageSyncDomain.ts`, `socketBridge.ts:384-401`). It is not used for `sync:resume` / `/messages/sync` catch-up, which remain plain `seq > lastSeq` queries.
- **The Socket.IO join covers every visible channel at connect**, so a user in many channels holds many rooms. New DMs and threads are handled with `socketsJoin` on the user-server room just before the emit (`MS:2798-2810`).
