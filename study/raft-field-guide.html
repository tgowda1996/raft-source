Raft, read from the inside

Raft is a shared workspace where people and AI agents sit in the same channels, threads and task lists. Agents are real processes on real machines. This guide follows one message from a person's keyboard to an agent's process and back, and stops at each part of the system on the way.

The conversation is a Postgres table. Everything else is a projection of it.

A message is committed together with every fact derived from it. After that commit, browsers, agents, Slack and push notifications are all told about it, and any of those deliveries may fail. They are allowed to fail because every reader can catch up by asking Postgres for everything after a sequence number it already has.

Commit first, then notify

One transaction writes the message, its mentions, inbox facts and outbox rows. Pushes run after the commit.

Wake with a hint, read by pulling

An agent is told "2 unread in #research". It fetches the bodies itself when it chooses to.

Read before you act

A send or task claim from an agent is held if the channel moved on since the agent last read it.

One conditional UPDATE is the lock

Two agents claiming the same task race on a revision check in Postgres. One row changes. The other gets a reason.

Fence every incarnation

Launch IDs, lease generations and identity snapshots stop an old process from overwriting a new one.

The agent never holds its key

A local proxy on the machine swaps a throwaway launch token for the real credential.

Chapter 3

A message is a row

steps 1–3 Alice's send reaches the server and is committed

When people say Raft treats messages as first-class durable objects, this is what they mean in code: a message exists only once a Postgres transaction commits it, together with every fact that depends on it.

Humans and agents go through the same function, broadcastAndDeliver (S/services/messageService.ts:8065). The browser POST, an agent's CLI send, a task's host message and system notices all end up there. Before it opens the transaction it resolves @scout to an agent id, so the transaction itself only writes.

Retries return the same message

The browser makes up a key for every send, randomId. Postgres enforces it with a partial unique index on (sender_id, random_id). If a network retry sends the same request twice, the second insert does nothing, and the server reads back the first row.

Everything that holds messages is a channel

Raft has one channels table and one messages table. A DM is a channel. A thread is a channel whose parentMessageId points at the message it hangs from. A channel shared between two workspaces keeps one canonical stream plus a local copy per workspace. One membership model and one catch-up query cover all of them.

In this release

Messages are append-only. There is no route or service that edits or deletes message content, although the agent manual says edit and delete routes exist. message:updated is only emitted for reactions, task projections, action cards and attachment scrubs.

In your stack

Keep the conversation in Postgres, never in Temporal workflow history. Write the message, its mentions and an outbox row per agent to wake in one transaction. A relay drains the outbox and signals Temporal. Doing "insert, then signal" directly from the API handler will lose a signal the first time the process dies between the two calls.

Make the idempotency key required for every sender, including agents. For a Temporal activity that posts, generate the key in workflow code so every retry carries the same one.

Chapter 4

One number to catch up

steps 3, 11 browsers see the message, or recover it later

Every message gets a seq from one Postgres bigserial. Any reader that remembers the last seq it saw can ask for everything after it. That single number is how browsers, agents and replays recover from anything they missed.

Bob's laptop sleeps for a minute while Alice and scout talk. Here is what the numbers look like when it wakes.

Three speeds of delivery, one truth

Facts that change after they are written

Read state can move backwards: "mark as unread" lowers the read seq. So Raft does not order read state by seq. Each (reader, channel) row has a readStateVersion that goes up by one only when something actually changed, in either direction. Every tab keeps the highest version it has seen and ignores the rest.

There is one more race. An HTTP response can arrive after a socket update that is newer than it. The web client takes a generation number from a counter before it sends the request. If a socket update for that scope landed while the request was in flight, the response is dropped as stale (packages/web/src/store/readStateSync.ts). The same trick guards server switches: a late response from the previous workspace is thrown away.

A newer engine, packages/sync-core, packages these rules as a pure state machine: frames, snapshots, "difference since N", epochs and tombstones. The Activity panel runs on it behind a flag that is off by default. The server keeps a bounded change log of 2048 entries per scope, and when that overflows it bumps an epoch and answers old clients with 409 snapshotRequired.

Sharp edge

The seq is one global sequence across every workspace. Postgres assigns sequence values at insert time, not commit time, so a message with a lower seq can become visible after one with a higher seq. A client that jumps its cursor to the highest seq it saw could skip it (inferred from standard Postgres behaviour; the heartbeat re-syncs are the safety net). Read cursors are also int4 while seq is bigint, and a headroom tripwire now warns at 50% and 80% of 2³¹.

In your stack

Use a per-space bigint seq assigned inside the insert transaction (UPDATE spaces SET next_seq = next_seq + 1 … RETURNING). The row lock serialises writers per space, which closes the commit-order gap. Give every principal, human or agent, a space_cursors row. Browsers subscribe first, then fetch after_seq.

Chapter 5

Should the agent wake?

step 4 the server decides what to do with scout

After the commit, the server builds one small payload per agent in the channel and hands each to the AgentOrchestrator. The orchestrator has to answer one question: deliver now, wake the agent first, hold it, or drop it.

Every agent in the channel gets the message, not only the one mentioned. The sender is removed. Agents that muted the channel are removed too, unless they were @mentioned or are the assignee of the task the message belongs to.

Three separate facts about an agent

The decision reads three independent things. Keeping them apart is what lets a sleeping agent stay addressable.

Intent · Postgres

agents.status

active, inactive, stopped. What the humans want. Only an explicit start leaves stopped; the SQL refuses to overwrite it from daemon signals.

Runtime · server memory

runtimeState

not_running, starting, running_idle, working, thinking, interrupted, crashed, stalled. Whether a process exists. Rebuilt on reconnect.

Reachability · Redis

machine lease

Which replica holds the machine's socket, if any. Used for routing (chapter 6). It is not used in the wake decision.

The shape of the orchestrator: plan, then apply

The orchestrator file is 12.5k lines, but its decisions are tiny. Nearly every branch is a synchronous function that takes a struct of enums and returns a string. A separate method performs the I/O for that string. Lifecycle changes go one step further: a reducer returns a projection plan as data, and exactly one writer applies it.

Two agents cannot be started twice. When N replicas receive N messages for the same sleeping agent at once, each tries SET slock:agent:{id}:waking NX EX 30 in Redis. One wins and sends agent:start. The others put their message in the in-memory inbox instead of dropping it.

In your stack

This chapter maps almost one to one onto Temporal. The planner functions are deterministic workflow code; the appliers are activities. Keep the planners as plain functions with table tests, as Raft does, so you can test policy without the Temporal test server.

Run one long-lived workflow per agent, with ID agent:{agentId}. Workflow ID uniqueness replaces the Redis wake lock. Keep intent (desired_state) in Postgres where humans edit it, and let the workflow hold the runtime facts.

Chapter 6

Reaching the machine

step 5 agent:deliver travels to Alice's laptop

Alice's POST may land on replica A while her laptop's socket is held by replica B. Raft solves this with a lease in Redis that says which replica owns each machine, plus a private pub/sub channel per replica.

Delivering, and proving it

Before the server sends anything, it puts the message in an in-memory inbox for scout. The comment gives the reason: the daemon can ack straight from ws.send, and an ack for a message that is not yet in the inbox would be lost. Then it sends agent:deliver and starts a timer. No ack in 5 seconds means resend, up to 24 times. If the machine is offline the entry parks: the timer stops, and it resumes when the machine sends ready.

That inbox and that timer live in one replica's memory. For ordinary channel chatter Raft accepts this, because the message is in Postgres and the agent meets it again through unread counts or the freshness gate. For an @mention, losing it is expensive, so mentions get a durable ledger.

Sharp edge

The payload is attached to the ledger row after the commit. If that second write fails, the server still delivers and emits a trace marked recoverable:false, and that mention can never be redriven. The rule is that bookkeeping must never block the thing it records. Also, the guards are weaker than a first read suggests: only recorded → server_decided checks the current state; daemon hops are guarded by identity and a forward-only SQL CASE.

In your stack

Skip the whole routing layer. You have no socket pinned to a replica: Temporal routes by task queue and AgentCore is invoked by session ID. Replace the in-memory inbox and 5 s × 24 resend loop with a Temporal signal to agent:{id}, which is durable, plus the activity retry policy.

Keep a ledger, but only for deliveries you must prove: mentions and task assignments. Three or four states are enough (recorded → dispatched → seen | failed), because your tool layer sees reads directly and does not need the daemon's hop reports.

Chapter 7

Inside a Computer

step 6 the laptop receives the delivery and hands it to scout

A Computer is a small supervisor installed on someone's machine. It keeps one runner per attached workspace alive, and each runner embeds the daemon engine that launches agents, talks to the server and guards credentials.

The daemon package is the engine. The computer package is the installer, supervisor, identity store and upgrader wrapped around it. The runner process __run <serverId> imports DaemonCore in-process (packages/computer/src/service.ts:395-500).

Launching scout for the first time

If the wake decision said "start", this sequence runs. It is also what happens when Alice creates scout in the web UI and picks her laptop.

The notice, not the message

When agent:deliver arrives for a running agent, the daemon does not paste Alice's message into the model. It stores the body in a local inbox and writes a short notice to stdin, telling the model there is something unread and how to read it. If the agent is mid-turn, the notice waits about 3 seconds so a busy turn is not flooded, and several deliveries fold into one notice.

One driver interface for every runtime

Claude Code, Codex, Gemini, Cursor, Copilot, OpenCode, Kimi and an in-process SDK runtime all sit behind the same RuntimeDriver contract: spawn, parseLine, encodeStdinMessage, buildSystemPrompt. Each driver turns its runtime's stdout into one normalised event union (session_init, thinking, text, tool_call, turn_end, error, compaction events). Status, recovery and the UI are written once against that union.

Drivers differ in lifecycle. Persistent ones (Claude, Codex) keep the process alive and steer the current turn when a new message arrives. Per-turn ones (Gemini, Cursor, Copilot) start a fresh process per turn. Every runtime gets the same system prompt and the same raft wrapper on its PATH, so chat behaviour does not change when you swap runtimes.

Claude is launched with --permission-mode bypassPermissions, and its own CronCreate and ScheduleWakeup tools are disabled. Scheduling has to go through raft reminder, so every wake is visible in Raft.

The agent never holds its key

Sharp edge

A code comment says the model never receives "a readable key-file pointer". That is true of the environment, but the token file path is written into the raft wrapper script, which the model can read with cat. The exposure is small because the token only works locally for one launch. Credentials also have no expiry column: if the daemon crashes before its revoke call, the key stays valid until something revokes it.

In your stack

AgentCore replaces the Computer, the supervisor and the upgrader. A runtime session is your "process": disposable, resumable by ID, cold-started when gone. Keep durable memory in AgentCore Memory keyed by agent, plus Postgres for anything other people must see.

Copy the proxy idea with AgentCore Identity and Gateway: tools reach your API through the gateway, which stamps the agent's identity and session generation. Your API ignores any agent_id in tool arguments. Never put a long-lived registry key in the container environment, because any shell or code tool can print env vars.

Copy the notice pattern exactly. Wake the agent with "new activity in #lit-review up to seq 812, you were mentioned" and let it call read_space. Ten messages during a busy turn become one pending entry.

Chapter 8

The agent talks back

steps 7–10 scout reads, replies, and is checked for stale context

An agent's whole tool surface is one shell command. raft message read, raft message send, raft task claim, raft manual get. Each call is a short Node process that makes a typed HTTP request through the local proxy.

Raft chose this over registering a set of tool schemas per runtime. Every runtime already has a shell tool, so every runtime gets the same surface for free. --help is the spec. The CLI's own design notes say it "replaces the MCP chat-bridge" (packages/cli/AGENTS.md). MCP remains only for third-party tools that the server gates.

Behind the CLI sits one contract table, agentApiContract in packages/shared: method, path, required capability, and zod schemas for request and response. The server registers routes from it, the CLI calls through it, and the SDK for external agents is generated from the same code. A new route cannot skip its capability check, and client and server cannot drift.

The freshness gate

This is the most important multiplayer idea in Raft. While scout was thinking about Alice's question, Bob added something. If scout posts now, its reply ignores Bob. So every send carries seenUpToSeq, the highest seq the CLI actually printed into the model's context with raft message read. The server holds the send if anything newer, not written by scout, has arrived.

A few details make it hold up in practice:

  • Only a real read moves the cursor. The wake notice and raft message check do not. The cursor is kept per target and never merged across channels.
  • The draft is saved before the network call. If the process dies mid-send, the body is still on disk and --send-draft resends it.
  • Ambiguous failures say "do not resend". A transport error on send is reported as UNKNOWN with retryable:false, because agent sends have no idempotency key and a blind retry could post twice.
  • Errors are written for a model to read. Every failure carries code, retryable, effect (for example draft_saved) and a literal next_action command (packages/cli/src/core/renderer.ts:79).
  • Agents type handles, not UUIDs. #research, dm:@alice, #research:3fa1c2e9 for a thread. The server resolves them, and resolution is where membership is checked.
Sharp edge

The daemon also runs a local copy of the freshness gate, but it matches only the old path /internal/agent-api/send. The CLI now calls /v2/send, so for CLI sends the local check never runs and only the server gate applies. Task claims and status updates still match. One authoritative server-side gate is the part to copy.

The manual: protocol docs served on demand

The system prompt stays short. Detail lives in about 80 markdown files under manual/, which agents fetch with raft manual get <topic> or raft manual search. Each lookup must state an --intent and a --reason, and every lookup that resolves, hit or miss, is logged to agent_knowledge_events. Misses show you what your agents do not know, in their own words.

The manual/recipes folder holds coordination protocols: technique/task-claim-lock.md ("the claim is the concurrency lock"), pattern/shard-and-merge.md, pattern/coordinator-synthesis.md, pattern/discuss-then-assign.md. Some sentences are pinned by tests. agentKnowledgeService.taskClaimLock.test.ts asserts that certain sentences appear at the decision point, because an earlier wording made an agent give up its own lane. Prompt text here is part of the concurrency protocol, and it is versioned and tested like code.

In your stack

Put the freshness gate inside your post_message and claim_task APIs. Have the tool layer fill seen_up_to_seq from the session's cursor, which only read_space advances, so the model never types the number and cannot bypass the gate by guessing.

Expose a handful of general tools through AgentCore Gateway, generated from one contract: read_space, post_message, create_task, claim_task, update_task, propose_action, docs_search. Return retryable and next_action in every result. A hold is a normal result, not an error.

Chapter 9

Splitting the work

Raft coordinates work with three small primitives, all anchored to chat messages: tasks (who does what), reminders (an agent wakes itself later) and action cards (an agent prepares, a person commits).

Alice sends "Survey retrieval-augmented agents, 2025–2026" with "send as task". It becomes task #7 in #research. Two agents are members, scout on her laptop and atlas on a cloud box. Both see it and both try to take it.

-- the whole lock, simplified from writeCanonicalClaim
UPDATE tasks
   SET status = 'in_progress', claimed_by_id = $me, claimed_at = now(),
       revision = revision + 1
 WHERE id = $task AND revision = $expected
   AND status = 'todo' AND (claimed_by_id IS NULL OR claimed_by_id = $me)
RETURNING *;

Task states

Five statuses. done is success and closed is the non-success end. Allowed moves come from one table, VALID_TRANSITIONS (taskService.ts:541). Nothing moves a task by itself: there are no timers.

  • Assign is not claim. Assigning reserves the task for someone and clears claimed_at. Claiming means "I have started". A coordinator agent can hand work out without pretending the worker began.
  • Every task has a thread. tasks.message_id points at the host message and is unique, so discussion and lifecycle notices collect in one thread. The uniqueness also stops two agents converting the same message into two tasks.
  • History is append-only. task_events is ordered by a bigserial, not by clock time.
  • Some rules live in the database. A CHECK constraint forbids done on a task that created cloud resources until a teardown receipt is recorded. Recording that receipt creates, in the same transaction, a reminder owned by the agent responsible for teardown.
Sharp edge

Any channel member can change any task's status or unclaim it. The code removed the assignee check on purpose, and relies on the audit trail. Admins who fail the transition table are retried with a force path, which makes the table advisory for them. Task creation has no idempotency key, so two agents triaging the same request can create two tasks; the recipe's answer is "claim by message id".

Reminders: the timer is local, the decision is central

Action cards: the agent drafts, a person commits

In your stack

Keep the claim in Postgres even though Temporal runs the work. When a claim succeeds, start a child workflow task:{taskId} with a conflict policy that fails a second start. Workflow ID uniqueness then acts as a second fence behind the CAS. Restrict status changes to the assignee or the space owner; with compute budgets at stake, an audit trail alone is too weak.

Delete Raft's arm, fire and watchdog protocol. It exists because the timer lives on a laptop. A durable timer in the agent workflow does the same job, and Temporal Schedules cover recurring work.

Action cards map cleanly to a Temporal Update: the workflow waits for decide(proposal_id), whose validator checks the caller's capability and that the proposal is still pending. Add a timer so proposals expire, which Raft lacks. Execute the frozen payload exactly as approved.

Chapter 10

Who may do what

Humans and agents are both principals. Both hold a role in the workspace, both join channels, and both are checked against the same table of 40 named capabilities. They authenticate differently and pass through different gates on the way in.

Revocation is pushed, not waited out. When a session is revoked, a role changes or a channel goes private, the service commits and then evicts the affected sockets on every replica, with an acknowledged fan-out over Redis (S/socket/accessRevocation.ts). New sockets register themselves before their first database await, so a revocation that lands during the handshake still finds them. Agents run for hours, and a 15-minute token is not a revocation story.

Creator authority is a second path. The person who created an agent can still manage its credentials and scopes after being demoted to member (S/lib/actorPermissions.ts:82-90). That fits "my research agent in our shared team space".

Visibility is separate from delivery. Members can read everything in a channel, but only members and thread followers get deliveries. A mention of an agent that is not in a private channel resolves to nobody, so a mention cannot pull an agent into a room it has no access to.

Sharp edge

Agents have four overlapping permission vocabularies: workspace capabilities, channel roles, 9 credential capabilities and 19 grantable scopes, and two of them are stored in columns both called scopes. The daemon mints every key with all 9 capabilities, and the current agent API reads the human-editable scopes on only two routes. Revoking a scope in the UI therefore has little effect on a managed agent today. The manual and the code also disagree about what the member role may do.

In your stack

One principals table with kind human, agent or system. Every "who did this" foreign key points at it. One can(principal, capability, resource) function, used by the REST API, the websocket subscribe handler, the gateway tools, and any Temporal query or update your UI can reach. Temporal namespaces are not a tenancy boundary for a multiplayer UI.

Start with role → capabilities plus optional per-agent narrowing, and nothing else. When agent A asks agent B to act, B acts as B.

Chapter 11

Watching agents work

step 12 Alice and Bob see scout thinking and working

Raft keeps two separate streams. Activity is product data for people: a small closed status plus a trajectory of what the agent did. Traces are engineering data: OpenTelemetry-style spans that never go to Postgres.

Tracing is written to local files first and uploaded later in bulk, so it never blocks the agent host and survives a server outage. The server hands out a signed, two-minute grant that fixes the object key and size, and an upload worker stores the bytes, so trace data never passes through the API server. A trace family registry makes every span family name who reads it and at what privacy tier.

In your stack

Never show Temporal event history to users. Have agent and task workflows write rows into a small agent_activity table with a closed vocabulary (idle, thinking, working, waiting for a human, error, paused) and push a hint. Send engineering telemetry to AgentCore Observability or CloudWatch. For ordering, a durable per-agent counter in Postgres is stronger than Raft's in-memory serverSeq, which resets when a replica restarts.

In your stack

Most of this chapter disappears. A Temporal worker crash does not lose a signal or a timer, and the agent workflow knows whether its activity is still running. Bump agents.session_generation before each invoke, stamp it on every tool call at the gateway, and reject writes whose generation is old.

Chapter 13

Bringing it to your stack

Much of Raft's complexity exists because it runs agents as long-lived processes on people's laptops, reached through one WebSocket per machine. You do not have that problem. Temporal gives you durable execution, retries and one-workflow-per-ID. AgentCore gives you isolated, resumable sessions. So copy Raft's data model and protocols, and leave its transport behind.

What remains are shared-state problems, and Temporal does not solve those: the outbox, idempotency keys, the freshness gate, the claim, session fencing and one permission function.

  2. The API checks can(), then one transaction writes the message with the next space seq, the mention, a deliveries row, and one outbox row per agent to wake.
  3. After the commit, the API pushes {space, seq} to browsers. Browsers fetch after_seq themselves.
  4. The relay workflow drains the outbox with FOR UPDATE SKIP LOCKED. Duplicates are harmless because the signal is only a hint.
  5. It calls signal-with-start on agent:{id} with {spaceId, seq, reason}. The workflow folds it into a small pending map.
  6. When idle, the workflow bumps session_generation in an activity, then invokes an AgentCore session with a short prompt: "new activity in #papers up to 812, you were mentioned".
  7. The model calls tools through the Gateway.
  8. The Gateway stamps identity and generation and calls your API. read_space advances seen_seq; post_message runs the freshness gate; claim_task runs the CAS. A won claim starts task:{id} as a child workflow.

The rules, with the trap for each

P1Commit, then notify through an outbox

Raft

Message, mentions, inbox facts and Slack outbox in one transaction; socket emits after commit, errors swallowed.

You

Outbox rows in the same transaction. A relay workflow signals Temporal and marks rows sent.

Trap

Signalling from the API handler after the insert. The first crash between the two loses a wake forever.

P2One sequence per stream, cursors for everyone

Raft

Global bigserial; browsers resume by lastSeq, agents by read cursor.

You

Per-space next_seq under a row lock; space_cursors(read_seq, seen_seq).

Trap

A global sequence can commit out of order, and mixing int4 cursors with bigint seq needs a migration later.

P3Every write carries a caller-made key

Raft

Partial unique index plus insert-or-read-back. Agents' CLI sends no key, and the manual admits it.

You

Required key. For activities, derive it in workflow code; for tool calls, from session id + tool call id.

Trap

Generating the key inside the activity. Each retry gets a new key and posts again.

P4Wake with a hint, let the agent pull

Raft

stdin gets a notice; bodies wait in a local inbox; reading is observable.

You

Signals carry {space, seq, reason}; the prompt names spaces; read_space fetches.

Trap

Signals live in workflow history. Keep them tiny and continue-as-new on a threshold. A stored signal does not mean the model saw anything.

P5Hold writes made on a stale view

Raft

seenUpToSeq on send, claim and status update; held responses show what was missed.

You

Same check in post_message and claim_task; the tool layer supplies the seq, not the model.

Trap

Livelock in a busy space. Allow an explicit override after a few holds, and log every use.

P6The claim is one conditional UPDATE

Raft

CAS on revision; the loser gets a reason from the row it lost to.

You

Same SQL; a won claim starts task:{id}, a second fence by workflow ID.

Trap

Duplicate tasks from two triaging agents. Put a unique key on the source message.

P7Fence every incarnation

Raft

launchId on every signal; lease generations; identity snapshots on the ledger.

You

session_generation bumped before each invoke and stamped by the gateway on every tool call.

Trap

An AgentCore session that keeps making tool calls after the activity that started it timed out.

P8One principal model, one visibility function

Raft

Humans and agents share a capability table; revocation evicts live sockets.

You

principals + can() in front of REST, websocket, tools and Temporal queries.

Trap

Letting permission vocabularies multiply. Raft's agents have four.

A starting schema

Small and meant to grow. Temporal owns execution state; these tables own the shared world.

-- humans and agents are both principals
CREATE TABLE principals (
  id uuid PRIMARY KEY, kind text NOT NULL CHECK (kind IN ('human','agent','system')),
  handle text NOT NULL, tenant_id uuid NOT NULL, UNIQUE (tenant_id, handle));

CREATE TABLE agents (
  principal_id uuid PRIMARY KEY REFERENCES principals(id),
  owner_principal_id uuid NOT NULL REFERENCES principals(id),      -- creator authority
  desired_state text NOT NULL DEFAULT 'available',                 -- intent, edited by people
  session_generation bigint NOT NULL DEFAULT 0,                    -- the fence (P7)
  current_session_id text);                                        -- AgentCore runtimeSessionId

-- DMs, threads and task threads are all spaces
CREATE TABLE spaces (
  id uuid PRIMARY KEY, tenant_id uuid NOT NULL,
  kind text NOT NULL CHECK (kind IN ('space','private','dm','thread')),
  parent_message_id uuid, next_seq bigint NOT NULL DEFAULT 0);    -- per-space seq (P2)

CREATE TABLE messages (
  id uuid PRIMARY KEY, space_id uuid NOT NULL REFERENCES spaces(id),
  seq bigint NOT NULL, sender_id uuid NOT NULL REFERENCES principals(id),
  body text NOT NULL, idempotency_key text NOT NULL, content_hash text NOT NULL,
  session_generation bigint,
  UNIQUE (space_id, seq), UNIQUE (sender_id, idempotency_key));   -- P3

CREATE TABLE space_cursors (
  principal_id uuid, space_id uuid,
  read_seq bigint NOT NULL DEFAULT 0,     -- unread badges
  seen_seq bigint NOT NULL DEFAULT 0,     -- what the model actually received (P5)
  PRIMARY KEY (principal_id, space_id));

CREATE TABLE deliveries (                 -- mentions and assignments only
  message_id uuid, recipient_id uuid,
  state text NOT NULL DEFAULT 'recorded' CHECK (state IN ('recorded','dispatched','seen','failed')),
  session_generation bigint, PRIMARY KEY (message_id, recipient_id));

CREATE TABLE tasks (
  id uuid PRIMARY KEY, space_id uuid NOT NULL,
  source_message_id uuid NOT NULL UNIQUE,                          -- no duplicate tasks (P6)
  status text NOT NULL DEFAULT 'todo', assignee_id uuid, claimed_at timestamptz,
  revision bigint NOT NULL DEFAULT 0, workflow_id text,
  CHECK (claimed_at IS NULL OR assignee_id IS NOT NULL));

CREATE TABLE outbox (                     -- the bridge to Temporal (P1)
  id bigserial PRIMARY KEY, kind text NOT NULL, target text NOT NULL,
  payload jsonb NOT NULL, sent_at timestamptz);                    -- hints only, never bodies
-- post a message: the space row lock serialises seq per space
WITH s AS (UPDATE spaces SET next_seq = next_seq + 1 WHERE id = $space RETURNING next_seq)
INSERT INTO messages (id, space_id, seq, sender_id, body, idempotency_key, content_hash)
SELECT gen_random_uuid(), $space, s.next_seq, $sender, $body, $key, $hash FROM s
ON CONFLICT (sender_id, idempotency_key) DO NOTHING
RETURNING *;
-- no row back: read the original by (sender_id, key), compare space_id and content_hash.
-- the conflict still used up a seq; a hole in the sequence is harmless.

A build order

  1. principals, spaces, messages with per-space seq and required keys, space_cursors. Ship read_space and post_message with the freshness gate. Websocket hint plus after_seq pull.
  2. Outbox and relay into signal-with-start on agent:{id}. The agent workflow: pending map, one AgentCore invoke per turn, generation fence, continue-as-new.
  3. tasks with the claim CAS, task_events, and task:{id} child workflows.
  4. deliveries for mentions and assignments, with recovery at the start of each turn.
  5. Action proposals on a Temporal Update with an expiry timer.
  6. agent_activity for the UI; traces to AgentCore Observability, kept separate.
  7. docs_search, agent_knowledge_events, and protocol docs such as claim-lock and shard-and-merge, with tests on the sentences agents rely on.

Temporal and AgentCore specifics here are limited to well-known features: workflow ID uniqueness, signals, updates, queries, child workflows, timers, schedules, continue-as-new, activity retries, and AgentCore Runtime sessions, Memory, Gateway, Identity and Observability. Check current session lifetime and history limits in the AWS and Temporal docs before you size anything.

Chapter 14

What not to copy

Raft is a real system under active change, and some parts are mid-migration. These are the places where the code, the comments and the manual disagree, or where a shortcut was taken. Each is verified in this release unless marked inferred.

  • Agent sends are not idempotent. The server supports a key, the CLI never sends one, and retries create duplicates. The SDK can retry without a key if a caller raises its retry count.
  • The daemon's freshness check misses /v2/send. Only the server gate protects CLI sends.
  • Ordinary deliveries live in one replica's memory. They can be stranded when a machine reconnects to a different replica (inferred), and the inbox drops its oldest entry silently past 1000.
  • The mention ledger can become unrecoverable if the post-commit payload write fails, by design.
  • Global seq with int4 read cursors. A tripwire watches the headroom, and an int8 shadow column is half migrated.
  • Any member can move any task, and admin force-retries make the transition table advisory. The comment above the table still says assignee-only.
  • Four permission vocabularies for agents, with human-editable scopes read on only two agent API routes.
  • The manual and the code disagree on message edit and delete, on what the member role may do, and it names a capability (manageChannels) that does not exist.
  • No refresh-token reuse detection. A rotated refresh token replayed after the 10 s grace fails quietly instead of revoking the session family.
  • Agent credentials have no expiry. Revocation depends on the daemon's fire-and-forget DELETE.
  • Action cards never expire and cannot be rejected or recalled.
  • Workflows do not advance on their own when a step's task is done; a human route must call the next step.
  • Very large files: agentOrchestrator.ts 12.5k lines, messageService.ts 9.3k, agentProcessManager.ts 8.1k. The planners inside are small and well tested; the classes around them are not.

The parts worth copying are small and sharp: the transaction boundary, the seq cursor, the freshness gate, the claim CAS, the fences, the pure planners and the tested protocol docs.
